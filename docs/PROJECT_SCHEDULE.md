# FindMyDoctor Project Schedule

This schedule follows Section 3.2, **Project Schedules**, in the SPMP. The SPMP describes a recommended 9-week prototype delivery baseline and allows parallel work where dependencies and staffing permit.

**Progress status:** Weeks 1–4 are marked done as requested. This status is a project progress marker and is not an independent verification of each deliverable.

| Week | Primary activities | Exit evidence | Status |
|---|---|---|---|
| Weeks 1–3 | Initiation, architecture, authentication, RBAC, OTP flows, doctor approval, admin provisioning, and web dashboards. | Approved baselines, role-protection tests, admin seed, and protected routes. | Done |
| Week 4 | Scheduling module (working hours, availability, break periods), capacity calculation (30-minute default), daily capacity configuration, and reservation system foundation. | Capacity calculation tests, schedule CRUD operations, and basic reservation tests. | Done |
| Week 5 | Unified queue management with sequential numbering, concurrency-safe queue assignment, automatic queue reassignment on cancellation with notifications, capacity enforcement across online and walk-in registrations, walk-in registration with temporary password generation, doctor-specific patient record check before booking, and mobile navigation to appointments view. | Booking/queue integration tests, conflict prevention tests, walk-in account lifecycle tests, concurrency-safe queue assignment tests, queue reassignment notification tests, and doctor-specific patient record validation tests. | Done |
| Week 6 | GCash payment flow (static QR code, receipt upload, verification states), additional charges, payment verification, and secretary-patient chat (conversation authorization and messaging). Payment total equals consultation fee plus additional charges. Walk-in patients may pay after consultation with secretary confirmation. Receipt upload never auto-marks payment as Paid (statuses: Unpaid, Pending Verification, Paid, Rejected). Notifications triggered for new secretary messages and payment verification using the notification module. | Payment state tests, receipt verification workflow, chat authorization tests, private receipt storage verification, total-amount calculation tests, and a test that patient-to-doctor messaging is blocked. | Not started |
| Week 7 | AI chatbot integration (safety and data minimization), consultation/visit records, medical history, prescription management, and PDF generation. AI conversation persistence (endpoints: /ai/chat and /ai/conversations), server-side-only AI API key handling, prescription-availability notification, and patient access limited to their own prescriptions and PDFs. A visit links to an appointment; a prescription contains items (medication, dosage, frequency, duration, instructions). | AI safety tests, data minimization verification, prescription PDF tests, medical-record association tests, a check that the AI key is never exposed to clients, and an authorization test that patients can only view their own prescriptions and PDFs. | Not started |
| Week 8 | Mobile integration with appointments, queue, history, prescriptions, and notifications; end-to-end role workflows. Waitlist feature (join waitlist and waitlist status notifications), patient cancel and reschedule of eligible appointments in mobile app, patient payments view (GCash QR and receipt upload), and patient queue visibility. Notifications: appointment changes (cancel/reschedule), prescription availability, waitlist updates, and notices to affected patients after a confirmed secretary/doctor exception or break-period change. Notification module foundation exists from earlier weeks. | Role-based end-to-end workflow tests, mobile feature integration tests, end-to-end test for schedule-change flow (exception/break change affecting active appointments -> confirmation -> affected-patient notification, with no auto-cancellation), end-to-end test for waitlist, end-to-end test for cancel/reschedule, and a check that ADMIN cannot perform clinic operations (schedules, capacity, queue, payments, consultation records). | Not started |
| Week 9 | Regression testing, performance/concurrency checks, privacy/security review, defect resolution, UAT, deployment, release notes, and handover. Asia/Manila timezone consistency check across appointments, queue entries, schedules, messages, notifications, and payments. Privacy/security review to confirm Supabase service role key and AI keys stay backend-only, receipts are not publicly accessible, and mobile/web never access PostgreSQL directly. Deployment as mobile and web clients reaching the backend API over HTTPS. | Timezone consistency results, security review findings, release candidate, UAT approval, and approved prototype release. | Not started |
